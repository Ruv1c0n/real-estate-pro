# scripts/bench — бенчмарки

Скрипты ручных замеров производительности по ТЗ. Запуск — из корня репо в Git Bash.

## coreapi-p95.sh — p95 времени GET списка (НФТ-10)

**Требование ТЗ (НФТ-10):** для 500+ объявлений p95 времени GET списка —
**< 300 мс с прогретым кэшем**, **< 500 мс без кэша**, при **одном
последовательном клиенте**; **100 запросов после прогрева**. В отчёте
фиксируются машина, состав данных и фильтры; сетевое время до внешних
площадок не учитывается.

Запуск:

```bash
# без фильтров
bash scripts/bench/coreapi-p95.sh

# с фильтрами (query-строка целиком в FILTERS)
FILTERS="deal_type=rent&city=Minsk&country=BY" bash scripts/bench/coreapi-p95.sh
```

Переменные окружения:

| Переменная        | Default                | Смысл                                   |
|-------------------|------------------------|-----------------------------------------|
| `COREAPI_BASE_URL`| `http://localhost:8000`| базовый URL core-api                     |
| `N`               | `100`                  | число замеров после прогрева (по ТЗ 100)|
| `WARMUP`          | `10`                   | прогревочных запросов до замеров        |
| `FILTERS`         | пусто                  | query-строка фильтров; пусто = GET без query |

Шаги скрипта: проверка `GET /health` (не 200 → «core-api не поднят»), проверка
`GET /api/v1/listings` (404 → «эндпоинт ещё не реализован — каркас для
issue #20»; на момент написания эндпоинта в core-api ещё нет — это осознанный
задел, не баг), `WARMUP` прогревочных запросов, затем `N` последовательных
замеров через `curl -w %{time_total}`. Вывод — `p50`/`p95`/`max` отдельными
строками и verdict «НФТ-10 (<300 мс с кэшем): выполняется/НЕ выполняется».

### Замер «без кэша» (< 500 мс) — вручную

Скрипт меряет только **тёплый** прогон (после `WARMUP` запросов кэш прогрет).
Холодный прогон автоматом не делается, потому что скрипт не владеет
инвалидацией кэша. Оператор делает так:

1. Замерить тёплый прогон скриптом (см. выше) — это p95 «с кэшем».
2. Выбить кэш одним из способов:
   - рестарт redis: `docker compose restart redis`;
   - либо точечная чистка ключей (если известен префикс кэша listings):
     `docker compose exec redis redis-cli --scan --pattern '<префикс>*' | xargs docker compose exec redis redis-cli DEL`.
3. Сразу (до прогрева) выполнить тот же скрипт, но с `WARMUP=1` — первый
   запрос будет холодным; либо собрать латентности вручную:

   ```bash
   for i in $(seq 1 100); do
     curl -o /dev/null -s -w '%{time_total}\n' \
       "http://localhost:8000/api/v1/listings?deal_type=rent&city=Minsk&country=BY"
   done | sort -n | awk '{v[NR]=$1} END {printf "p95: %.1f мс\n", v[int(0.95*NR+0.999)]*1000}'
   ```

4. Сверить с порогом НФТ-10: p95 без кэша **< 500 мс**.

### Что фиксировать в отчёте (по ТЗ)

- **Машина** — модель CPU/RAM/ОС, куда стенд развёрнут (фиксирует оператор).
- **Состав данных** — замер по ТЗ делается на **500+ объявлениях**. Сейчас
  такого дампа в стенде нет — он появится вместе с collector/mock-avito
  (Дима/Тимур); до этого результаты — дымовые, не приёмочные.
- **Фильтры** — точная query-строка (`FILTERS=...`) или «без фильтров».
