# Быстрый старт по схеме core — для разработчиков

Для Тимура (модели SQLAlchemy, запросы) и Димы (дамп, UI): как поднять базу,
как её читать и писать, какие правила зашиты в схеме. Автор схемы: Илья.
Полные источники: `docs/core-schema-draft.md` (решения ревью, в main),
`docs/er-diagram.md` (картинка, PR #86), `docs/query-analysis.md` (индексы
и планы, PR #84), `docs/db-backup-restore.md` (бэкапы, PR #83) — соседние
документы приезжают в main вместе со своими PR, поэтому здесь они даны
путями, без ссылок (линтер ссылок гоняется на merge-состоянии одного PR).

## Подъём базы

```bash
docker compose up -d postgres          # БД (учётка из .env / .env.example)
cd core-api
alembic upgrade head                   # применить миграции (0001 схема, 0002 роли,
                                       # 0003 FK-индексы/CHECK, 0004 DDL notifier)
alembic current                        # текущая версия (0004)
alembic downgrade 0001                 # откат (роли удалятся, таблицы останутся)
alembic upgrade head                   # и вернуть
```

Подключение из кода — `DATABASE_URL` из `.env.example` (драйвер строго
`postgresql+asyncpg`). Прогон миграций в CI — та же команда, джоба активируется
автоматически (alembic.ini в core-api уже есть).

## Карта таблиц

| Таблица | Назначение | Ключевые правила |
|---|---|---|
| `countries` | ISO alpha-2 → название | PK `code` CHAR(2) верхним регистром |
| `cities` | канонические города внутри страны | `UNIQUE (country_code, name)`; `UNIQUE (id, country_code)` — цель составного FK |
| `city_name_aliases` | альтернативные написания городов | хранятся **уже нормализованными** (lower + trim); поиск: `WHERE alias = lower(trim(:input))` |
| `sources` | источники объявлений | `code` уникален ('mock', 'avito'), есть человекочитаемое `name` |
| `currencies` | курсы к USD | `rate_to_usd` — стоимость единицы валюты в USD, USD = 1; демо-константы (ТЗ 3.2) |
| `listings` | объявления | см. «Дедупликация» и «Деньги» ниже |
| `listing_photos` | фото объявления | `ON DELETE CASCADE` вместе с объявлением |
| `listing_duplicates` | связи «возможный дубль» | пары `CHECK (listing_a_id < listing_b_id)`; **обе** записи сохраняются |
| `outbox_events` | очередь публикации + инвалидация кэша | см. «Outbox» ниже |

Справочники заполняются **только миграциями** — автоматически создавать
страны/города/валюты из входящих объявлений нельзя (ТЗ 3.7), неизвестные
значения → 422.

## Дедупликация (ТЗ 3.3) — контракт для реализации

- Тождество объявления = пара `(source_id, external_id)` —
  `UNIQUE (source_id, external_id)`. Дубль POST → `200 {"id": ..., "created": false}`,
  новое объявление → `201`, новое outbox-задание **не создаётся**.
- `url_hash` = SHA-256 однозначной сериализации пары `(source, external_id)`;
  имя поля историческое, алгоритм сериализации фиксируется в contracts.md
  при реализации адаптера. `UNIQUE (url_hash)`.
- `content_hash` = SHA-256(city + country + address + rooms + area + deal_type),
  считает Core API при вставке. Совпадение у разных источников → запись в
  `listing_duplicates` (пару писать как `(min_id, max_id)`); при неполных данных
  (например, area=NULL у одной из записей) автоматическое связывание не выполняется.

## Деньги (ТЗ 3.2)

`price_usd` вычисляет **Core API** и проверяет по тому же курсу:
`price × rate_to_usd`, `Decimal`, округление `ROUND_HALF_UP` до целого USD.
В Python — только `Decimal` (`NUMERIC` в БД), **не float**. Демо-курсы —
константы из миграции 0001, менять их в рантайме нельзя.

## Outbox (ТЗ 4.3)

- Запись объявления и задания — **одна транзакция**.
- `event_id` — устойчивый UUID задания (ФТ-2.5): колонка и `payload.event_id` —
  **одно и то же значение**; повторная публикация не меняет UUID.
- Очередь: `WHERE published_at IS NULL ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED`;
  после XADD в `listings.new` — `UPDATE published_at = now()`. Ошибка Redis —
  задание остаётся в очереди.
- `kind='cache_invalidate'` из стрима не публикуется: воркер Core API сам читает
  эти задания и делает `INCR cache:version`.

## Идентичности и массовая вставка (важно для дампа)

id объявлений — `GENERATED BY DEFAULT AS IDENTITY`: явные значения разрешены
(удобно для фикстур дампа с постоянными ID), но после ручных вставок
последовательность надо выровнять, иначе следующие INSERT словят конфликт PK:

```sql
SELECT setval(pg_get_serial_sequence('core.listings', 'id'),
              (SELECT max(id) FROM core.listings));
```

`TRUNCATE core.listings RESTART IDENTITY CASCADE` чистит и photos/duplicates/outbox.

## Типовые запросы (ФТ-2.2,contracts.md)

```sql
-- основной фид: тип сделки + город + диапазон цены, дефолтная сортировка
SELECT id, title, price_usd, created_at
FROM core.listings
WHERE deal_type = :deal_type AND city_id = :city_id
  AND price_usd BETWEEN :min AND :max
ORDER BY created_at DESC, id DESC      -- date_desc; вторичный ключ id
LIMIT :size OFFSET :offset;

-- сортировка по цене: price_asc / price_desc — всегда с tie-breaker по id
ORDER BY price_usd ASC, id ASC

-- «возможные дубли» объявления
SELECT listing_a_id, listing_b_id
FROM core.listing_duplicates
WHERE content_hash = :content_hash;
```

Индексы под это уже стоят (см. query-analysis.md): составной
`(deal_type, city_id, price_usd)`, `(created_at DESC)`, `(rooms)`, `(area_m2)`,
`(content_hash)`. Пустая страница — валидный `200` (контракт), запросы работают.

## Роли (миграции 0002 и 0004)

Созданы роли `core_api` (только схема `core`) и `notifier` (только `notifier`),
без паролей — пароли выдаются при депое (см. план координации в PR #82).
Миграция 0004 добавила роли `notifier` DDL её схемы (CREATE) и владение её
таблицами: встроенный раннер SQL-миграций notifier работает под сервисной
ролью, пары `NOTIFIER_DB_USER/NOTIFIER_DB_PASSWORD` включать можно. Пока
переключение не выполнено, сервисы ходят под `app`; дефолтный режим 0004 не
затронут — `app` сохраняет DML на таблицы notifier. Права сервисов:

```sql
SELECT has_table_privilege('core_api', 'core.listings', 'SELECT');   -- true
SELECT has_schema_privilege('notifier', 'core', 'USAGE');            -- false
SELECT has_schema_privilege('notifier', 'notifier', 'CREATE');       -- true (0004)
SELECT has_database_privilege('notifier', current_database(), 'CREATE'); -- false
```

## Частые грабли

- `alembic_version` лежит в `public` — служебная, не удалять и не переносить.
- `pg_restore --clean` сносит гранты вместе со схемой: после него обязателен
  цикл `alembic downgrade 0001 && alembic upgrade head` — см.
  `docs/db-backup-restore.md` (PR #83).
- Вставка города/страны из кода — нарушение ТЗ 3.7; расширение справочников —
  новая миграция.
- `price_usd`/`rooms`/`area_m2`/`price` защищены CHECK'ами (`> 0`, `rooms >= 0`,
  `area NULL OR > 0`) — БД не примет невалидные значения даже мимо Pydantic.
- Пароли в миграциях не появляются в принципе: секреты только в `.env`.
