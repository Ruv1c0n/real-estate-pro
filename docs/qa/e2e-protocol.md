# Протокол приёмки: сквозной прогон и замеры НФТ-10/11 (issue #20)

Подготовлено: 2026-11-16, Даниил (зона сквозной интеграции, ТЗ 6.4). Язык протокола — русский (внутренний документ).
Первые источники: ТЗ v1.1 (разделы 3.6, 4.4, 5.2–5.3), contracts.md §2 (PR #24).

## 0. Когда прогон возможен

Протокол прогоняется после закрытия критического пути: справочники core-api (ФТ-2.4) → POST /api/v1/listings (ФТ-2.1) → outbox (ФТ-2.5) → collector (ФТ-1.x). До этого доступен **частичный прогон** сценариев S2, S5–S6, S9 (публикация через `/debug/event`, минуя collector/outbox).

Отметка сценария: `[ ]` — не выполнен, `[x]` — пройден, `[~]` — пройден частично (расшифровать).

## 1. Предусловия

- [ ] `.env` заполнен (НФТ-1): `TELEGRAM_BOT_TOKEN` (или осознанный log-режим), `ADMIN_KEY`, `POSTGRES_*`;
- [ ] `docker compose up --build` — 5 сервисов healthy в правильном порядке (postgres/redis → core-api `/health/ready` → collector, notifier) — НФТ-8;
- [ ] справочники заполнены миграциями (ТЗ 3.7): `GET /api/v1/countries` не пустой → notifier `/health` показывает `dicts:true`;
- [ ] тестовый дамп 500+ объектов / 5 стран / 10 городов загружен (ТЗ 3.4, с collector/mock-avito);
- [ ] машина замера зафиксирована в отчёте (НФТ-10: модель CPU/RAM; часовой сдвиг оператора/БД для НФТ-11).

## 2. Сценарии

### S1. Стартовая конфигурация
- [ ] все healthchecks зелёные; лог старта notifier содержит строку `config:` с параметрами (лимит/воркеры/порог — значения ТЗ или заданные env);
- [ ] повторный `up` без `down -v` не теряет данные (НФТ-5).

### S2. Прямая публикация (без collector, доступен раньше остальных)
- [ ] `POST /debug/event` с валидным payload (X-Admin-Key) → у подписанного чата приходит уведомление Telegram (или запись в log-режиме), `sent_at` в `notifications_log`;
- [ ] невалидный payload → запись в `listings.dead` с причиной и ID → событие подтверждено, в чат ничего не уходит (ТЗ 4.3);
- [ ] без X-Admin-Key → 401/404 (НФТ-3).

### S3. Полный поток (ТЗ 4.4)
- [ ] collector: `POST /collect/run` (202, run_id) → дамп 500+ через POST /api/v1/listings → core-api: новые 201, повторы 200 {created:false};
- [ ] outbox: каждая новая запись → событие `listings.new` (XLEN соответствует числу новых); ответ 200/201 у POST получен раньше XADD — публикация фоновой задачей (ФТ-2.5);
- [ ] notifier доставляет подписчикам; дедуп: повторная публикация того же объявления → БЕЗ нового уведомления (UNIQUE chat_id+listing_id);
- [ ] `content_hash`-дубль между источниками → обе записи сохранены, связь «возможный дубль» (ТЗ 3.3) — проверка в БД core.

### S4. Подписки и матчинг (ФТ-3.1, 3.4)
- [ ] /start, /subscribe (валидная), /list, /unsubscribe — полный цикл;
- [ ] невалидная подписка (неизвестный город/страна) отклоняется с понятным сообщением;
- [ ] 11-я подписка отклоняется (лимит 10);
- [ ] две подписки одного чата под одно объявление → **одно** уведомление;
- [ ] матчинг по всем заданным критериям (deal_type/city/rooms/price) — нерелевантное объявление не доставляется.

### S5. Лимит и отложенные (ТЗ 3.6)
- [ ] `NOTIFIER_NOTIFICATIONS_PER_HOUR=2` на стенде; 3-е уведомление часа → deferred в PG (`status='deferred'`), НЕ отброшено, pending-событие подтверждено;
- [ ] после истечения окна флешер доставляет отложенное; retry не «перекручивает» очередь (available_at, PR #72);
- [ ] параллельный клейм: два прохода не задваивают доставку (журнал/UNIQUE).

### S6. /stop (ТЗ 4.2)
- [ ] /stop при непустой очереди: users/subscriptions/notifications_log/deferred чата пусты (каскад), сообщение после /stop не приходит;
- [ ] /start заново работает;
- [ ] [если #70 смержен] отложенное задание удалённого пользователя снимается без отправки; [если #73 смержен] /stop чистит очередь и в memory-режиме.

### S7. Устойчивость (НФТ-7, 8; ТЗ 4.3)
- [ ] рестарт notifier при непустом stream: непрочитанные и pending догоняются, дублей нет;
- [ ] рестарт Redis: данные живы (AOF everysec); потеря последнего интервала — осознанная граница;
- [ ] chaos mock-avito (429/500) на фоне сбора: collector повторяет (ФТ-1.6), core-api и notifier не падают;
- [ ] остановка postgres на 30 с при потоке событий: события остаются в pending (PR #68), после восстановления доставляются ровно один раз;
- [ ] [если #73 смержен] reaper чистит stream только за безопасной границей: pending-записи остаются.

### S8. Замер НФТ-11 (log-режим допускается: «в log-режиме измеряется запись совпадения»)
- [ ] каркас: `scripts/bench/notifier-p95.sh` (N=100, INTERVAL=5s, подписка под тестовый город, notifier в log-режиме без токена);
- [ ] поток ≤1 событие/5с, ≥100 событий; p95 **< 5 с** — требование;
- [ ] в отчёте: p50/p95/max, машина, часовой сдвиг оператора↔БД; аварийные интервалы/лимит/Retry-After в замер не входят (за фильтрацией следит оператор);
- [ ] эталон каркаса: 16.11 локальный прогон N=10 → p95 = 109 мс.

### S9. Замер НФТ-10
- [ ] 500+ объявлений в core; `scripts/bench/coreapi-p95.sh` N=100 после прогрева: p95 **< 300 мс**;
- [ ] холодный прогон (чистка кэша/рестарт redis): p95 **< 500 мс**;
- [ ] в отчёте: машина, состав данных, использованные фильтры.

### S10. Безопасность и ошибки (НФТ-1, 2, 3, 12)
- [ ] секреты только в `.env` (gitleaks зелёный), не в логах;
- [ ] ошибки JSON API: `{error, message}` с корректными кодами, включая 422 валидации RawListing и фильтров.
