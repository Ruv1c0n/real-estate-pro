# Runbook: резервное копирование и проверка восстановления (ТЗ 6.1)

Зоны: схема/данные — Илья; механика запуска (compose/скрипты) — Даниил. Скрипты работают с живым compose-стендом, ничего не поднимают и не гасят.

## Ежедневный бэкап

```bash
bash scripts/ops/backup.sh
# → backups/realestate-YYYYMMDD-HHMMSS.sql.gz (схемы core + notifier)
```

- `BACKUP_DIR` держи вне репо или добавь в `.gitignore` — дампы содержат пользовательские данные.
- Храни минимум 3 последних снимка (учебный уровень; ротация — руками или `ls -t backups/* | tail -n +4 | xargs rm`).

## Проверка восстановления (обязательная половина ТЗ 6.1)

Бэкап без проверки восстановления — не бэкап:

```bash
bash scripts/ops/backup.sh                 # свежий снимок
bash scripts/ops/restore.sh backups/realestate-<ts>.sql.gz
# → восстанавливает в отдельную БД realestate_restore_check (НЕ трогает рабочую)
#   и печатает количество записей users/subscriptions/notifications_log
```

Чек-лист проверки (отметить в отчёте):
- [ ] restore завершился с кодом 0, без `ON_ERROR_STOP`-ошибок;
- [ ] счётчики таблиц совпали с рабочей БД (по выводу restore.sh);
- [ ] контрольная выборка: случайная подписка из рабочей БД есть в restore-БД;
- [ ] после проверки restore-БД удалена (`DROP DATABASE realestate_restore_check`).

## Границы гарантий (ТЗ 4.3 / НФТ-5)

- Redis в бэкап не входит: кэш и `dedup:urls` восстанавливаются (ТЗ 3.3), stream `listings.new` — НЕ восстанавливается из дампа; недоставленные события после аварии Redis теряются в пределах AOF-интервала (осознанная граница ТЗ).
- Миграции повторно применяются раннером при старте notifier; дамп содержит схему целиком — после restore раннер ничего не накатывает (версии уже в базе).

## Когда обновлять этот runbook

При появлении схемы core (Alembic, Илья) — добавить её таблицы в счётчики restore-проверки и в `--schemas` backup.sh (схема `core` уже включена в pg_dump наперёд).
