Дата замера: 2026-11-17. Режим: **log** (ТЗ НФТ-11: «в log-режиме измеряется запись совпадения»). Замер выполняется по протоколу `docs/qa/e2e-protocol.md` (S8), скрипт `scripts/bench/notifier-p95.sh` (PR #73). Часть issue #20.

|---|---|---|
| **p95** | **99 мс** | < 5 000 мс — **выполнено (запас ~×50)** |

Латентность — от фиксации `t0` (публикация через `POST /debug/event`, X-Admin-Key) до `sent_at` в `notifications_log`; p50/p95/max методом ближайшего ранга.

## Условия замера (НФТ-10: «фиксируются машина, состав данных и фильтры»)

- **Машина:** AMD Ryzen 7 7800X3D (8 ядер), 63 ГБ RAM, Windows 11, Docker Desktop (контейнеры postgres:16, redis:7 с живым notifier-бинарём на хосте).
- **Сборка:** notifier `feat/notifier-ops-completeness` @ `c4f732b` (этап 2 + R-поезд + надёжностная волна: клейм/чат-лок, условный XACK, UserExists).
- **Профиль нагрузки:** 100 событий, интервал 5 с (≤1 событие/5 с), подписка rent/BY/Minsk (1 подписка, 1 пользователь, chat 990001 — удалён после замера).
- **Режим:** log (без `TELEGRAM_BOT_TOKEN`); `sent_at` в UTC, `t0` на машине оператора — расхождение часов входит в результат.
- **Свободный лимит:** `NOTIFIER_NOTIFICATIONS_PER_HOUR=100` — по НФТ-11 замер идёт «при свободном лимите пользователя»; лимитные задержки и аварии в результат не входят (за фильтрацией следит оператор).
- Дата: 2026-11-17, ~01:00 МСК.

## Отклонения в ходе замера (зафиксировано для честности)

1. **Первый прогон забракован оператором**: notifier был запущен с ТЗ-лимитом 30/час — с 31-го события уведомления уходили в `deferred` и в замер не попадали (78 «пропуск»-строк). Это **не дефект, а живое подтверждение ТЗ 3.6**: превышение лимита откладывает задания в PostgreSQL, не отбрасывая. Приёмочный прогон restarted на чистых данных со свободным лимитом.
2. Признак деградации при повторе: дедуп (UNIQUE chat_id+listing_id) отработал на повторных публикациях — вторых записей не появлялось.

## Границы этого замера

- Замеряется **только notifier-нога**: от публикации события в stream до записи результата. Полное p95 «от фиксации объявления» (ТЗ 4.4: collector → core → outbox → stream) будет замеряться в issue #20 после M2 (outbox) — скрипт тот же, `t0` переносится на момент фиксации в core-api.
- Порог без кэша/прогрева не применим (это не GET-замер; НФТ-10 — отдельно).

## Вердикт

**НФТ-11 выполняется с запасом ~×50** на notifier-ноге при профиле нагрузки ТЗ. Финальный сквозной замер — в issue #20 после outbox (M2).
